## 0. 意思決定の結論（従来のR125〜R304工程数前提を撤回）
目標は「未知の自然言語指示から、独創性と用途を備えた3D建築を生成し、Minecraft Educationの試験ワールドで使える状態にする」こと。**LLMの建築発想能力を一から実装し直さず、既存LLMと既存の幾何/検証コードを接続する。**
ただし、LLMが建築の説明を出力できることと、実用的な床・入口・階段を備えた3Dの生成に成功することは異なる。実モデルの成功率、Minecraftでの歩行、美術品質、Macの速度はそれぞれ実測する。成果不明のまま完成を宣言しない。
旧180工程予測は廃止。以後、工程番号を増やすのではなく「一つの端から端まで動く成果」を最優先にする。

## 2. 最小のシステム構成（薄い縦貫パイプライン）
1. **自然言語:** 目的、必要な部屋、階数、敷地、雰囲気、制約、優先順位を受け取る。指定がなければ不必要な質問はせず明示的な既定値を使う。
2. **LLMによる創造:** Qwen/Gemmaがコンセプト・ゾーニング・部屋の関係・屋根/外殻・動線方針を自分で考える。住宅・図書館などの名称に対応した固定配置は選ばない。
3. **コンパクトな意味設計（ArchitecturePlan IR）:** 目的、階/ゾーン、用途・隣接関係、入口/垂直移動、形状の主役、採光方針、空き領域、材料意図、未充足要件を構造化する。**IRは自由な構成を支える中間表現であり、36個の固定部材リストではない**。モデルサイズに応じ、最大出力長を設定。設計IRと実座標の生成責任を分離する。
4. **共通の形状生成器:** IRをB143などの検証可能な実3Dソースへ変換。外殻・床・入口・空洞・階段の連続性を整合させる。LLMが生成した高度な幾何コードは将来のオプションとし、最初は信頼されたコンパイラのデータ入力経路で動く。
5. **共通検証:** スキーマ/上限、入口→用途空間への経路、頭上空気、支持床、上下階、空洞、干渉、素材/敷地境界、ユーザー要求との意味的一致をそれぞれ判定。検出した失敗を短い機械可読フィードバックにする。
6. **限定修復:** まず構造欠陥のある部位を一般ロジックで直す。LLMへ戻す場合は失敗箇所・構造上の根拠を伝え、モデル呼び直しは最初は最大2回。失敗ならHOLDして別案生成を優先。欠陥が直るまで一つの建物だけを無期限に修正しない。
7. **Minecraftアダプタ:** 実3DのボクセルをMinecraft Educationの対応ブロックへ変換し、位置決め・命令バッチ化・差分・進捗・中断・再開・復元を担う。**データのコンパイルと世界への書込みは別プロセス/別承認ゲート**。
8. **試験ワールド・美術:** 明示された試験ワールド内に施工し、入口・階段・部屋を現物確認。美術は複数視点の実3Dと人の評価で確認し、プローブ合格のみで美術PASSにしない。

### 小型モデルと大型モデルの役割分担
- **基本モード:** Macの8GB級Apple Siliconを視野に入れ、2B級4bitモデルが短いArchitecturePlan IRを出力し、非LLMエンジンが正確な構築を行う。16GBでは4B級も検証。ランタイム/量子化の対応は環境で確かめる。
- **高度モード:** 27B級などは複雑な構想、複数案比較、創造性の向上に使う。ただし基本的な住宅・小施設は27B依存にしない。
- **任意のコード生成:** 高度な自由形状に対してはモデル生成スクリプトも研究できるが、**OSコマンド、ファイル/networkアクセス、任意コード実行を直接許可しない**。本物の隔離プロセス/コンテナと時間・メモリ・計算量制限、入出力形式を備えるまで無効。Node vmを唯一の保護手段にしない。
- 量子化モデルの可用性、Mac 8GBでのメモリ・処理時間、GPU/CPU設定は現時点で未実測。特定モデルの動作を保証しない。

## 3. 最短で動かす「最初の完成」＝MVPの契約
**MVPは、豪華な建物を毎回生成することではない。** 少なくとも「初見の指示→モデルが独自の設計→1棟の真正3D→実空間QA→Minecraft Educationの試験施工→人が入って確認」が一度つながること。
- 題材は図書館に固定しない。最初は住宅・店舗・小研究施設の異なる3種類を用い、設計要求や平面が明確に異なることを確認する。実施ログはモデル名、量子化、プロンプト、seed/設定、IR/ソース/形状SHA、時間、メモリ、施工座標、検査結果と結びつける。
- 最初の最低機能は、**外観 + 支持床 + 入口の開口 + 少なくとも2機能領域 + 屋根 + 窓 + 入口から各用途へ連続する動線**。2階以上なら階段と上下階への接続が追加必須。該当しない要素は理由を記録する。
- 固定の家テンプレートに各用途ラベルを変えて当てはめたものは「汎用成功」ではない。LLMが意思決定した箇所と、共通エンジンが決定した箇所を証拠に残す。
- 試験ワールドへの施工結果、Minecraft内歩行、画像/録画、ユーザー美術評価、ソースのCI評価は別々に記録する。Aソース成功/B実形状成功/C美術判定/Dワールド内成功/E実LLM創造成功を混同しない。

## 5. 評価指標・反証可能な成功条件
- **真の生成率:** モデル出力→コンパイル→幾何評価に至った比率。ダミー応答と実モデルを分け、最低3反復/条件から開始。数字は目標であり初期実績ではない。
- **用途充足率:** 未知の依頼の「必要な部屋・機能・入口・景観」の独立チェック。モデル自身が宣言した評価項目だけではPASSとしない。
- **3D利用性:** 空間の空き、支持床、入口、階段、上下動線、目的地到達、閉塞、内外連続。Minecraft実歩行を区別する。
- **美術品質:** 正面/斜視/側面/俯瞰/入口/内部/上下接続の真正3Dで人間が比較し、単なる箱・意味のない大量部材を不合格にできるようにする。好みを一つのスコアだけに潰さない。
- **多様性:** 住宅/店舗/研究施設等の独立した新規要求に応じて、ゾーニング、構造、外形が具体的に違うことを確認。既存の12作成+4改修課題を回帰に使い、さらに開発中に使わない保持課題を別管理。
- **Macリソース:** 起動/常駐/生成ピークメモリ、swap・メモリ圧迫、初回/ウォーム生成時間、出力トークン、品質。速さの目標値は実Mac計測後に合意し、未計測の数字を成功条件として捏造しない。
- **実運用:** 施工コマンド数、所要時間、途中停止・再開・復元の結果、壊した元ブロックの差分、ゲーム内の歩行/採光/見た目。
- 各成果を「実モデルかテストダブルか」「実3Dか概略図か」「Minecraft実施工かソースのみか」で必ず区別。

## 6. 世界への書込に関する境界
2026-10-24のユーザー包括許可で、Qwen/Gemmaローカル推論・モデル切替・Minecraft試験施工は都度承認不要。ただし有料API、ユーザーPCへのWork/Computer Use、mainマージ等は含まれない。
1. 実ワールドへ触るコンポーネントは、読み取り専用の計画/検査系から独立させる。
2. 許可対象は**正確に識別できる試験ワールド**。ワールド識別不能、既存建築との重なり、範囲外、バックアップ/復元不能、対応しないコマンド形式なら実行を停止。
3. Block palette / 短い操作列へ変換し、座標・材質・予想範囲・破壊対象・操作数・バックアップ参照・失敗時中断を表した具体的BuildPlanを生成して技術ゲートを検査する。
4. B143は構造上BuildPlanが空の**デザイン用コンパイラ**。その安全フラグを勝手にPASSへ書き換えず、別のworld adapterがワールド個別の施工許可状態を生成する。
5. 一部失敗は正常に検出してHOLD。試験ワールド内の施工・読み戻し・実歩行後にのみD成功を宣言する。
6. 元B143/B143-Qwen/Freeze・既存世界を破壊しない。バックアップ・差分と正常復帰を工程の一部に含む。

## 7. 開発効率と固執の再発防止
- **工程を増やすことを成果にしない**。旧R125〜R304予定を機械的に消化せず、最小の縦貫成果に必要な改修を束ねてコミットする。
- 同一建築の局所修正は原則2回まで。次は他用途で同じ不具合が発生するか検証し、問題が共通なら生成器/評価器側の修正として解く。無限修正ループ禁止。
- 既存12+4ケースと少数の本物の初見課題を使う。未達ケースはHOLDに記録し、対象建築の完成だけに時間を使わない。
- 追加ライブラリ・新ファイル・新ワークフロー・別PRは実装に不可欠な場合に限定。過去に生成した同じソース・同じメッシュはSHAベースのキャッシュで再利用。CIは差分に必要な軽量検査のみ常時、重い実3D比較は節目に実行。
- README→憲章→現在地→直近計画を短い入口にし、長いR番号の履歴は凍結。GitHubにモデルや現物の根拠を保存し、ユーザーに毎日のZIPアップロードや長文引き継ぎを要求しない。
- 「技術的には難しくない」仮説はMVP成功で検証する。実際のモデル・変換・Minecraft接続が難しければ阻害要因と追加コストを明示して方針を調整する。簡単だと断定して未完成を隠さない。
