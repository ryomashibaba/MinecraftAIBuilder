# R125 — 縦貫MVP実装計画（意思決定と着手チェックリスト）
基準日：2026-10-24 JST。上位計画：[MinecraftAIBuilder戦略 v2](PROJECT_STRATEGY_V2_JA.md)。
**この文書は作業指示であり、現時点でMVP完成・Mac実機測定・Minecraft施工が済んだという記録ではない。**

## R125で最初にすべきこと
目的：**「Qwen/Gemmaによる未知の住宅などの設計」→「既存B143 3D」→「実Minecraft Education試験施工」** までの阻害要因を最少の実装量で解く。R125を新しい図書館改修に充てない。

### P0：最短経路の実物確認
- 既存 source/ai/b198g-local-model-adapter.mjs と scripts/b198h-local-workflow.mjs を使い、利用可能なローカルQwen/Gemmaモデルを検出。Qwen3.8-27B等は既存機種の実測比較用で、基本モードの必須モデルにしない。
- 建築要求3種：**小さな二階建て住宅／入口付き店舗／小研究施設**。図書館は対象外。最初は1件を実モデルで動かし、同じ処理を別2件にも再利用する。
- B143 compileDesign が6形状、ADD/CUT、repeat、階段、ボクセル化を持つことを再確認。新しい全機能ライブラリをいきなり作らない。
- Minecraft Educationへの実行方法を現在の環境で確認（許可された接続口、MakeCode/コマンド、世界の識別、実際の書込・復元が可能か）。**未確認なら「施工済み」と書かない**。手動アップロードや毎回CMDを強要しない。
- 既存のB198B 12+4固定ベンチマークは改変せず保持。3件の先行試行とは分ける。

### P1：実モデル最小ループ
- 初見の指示→ローカルモデル応答→厳格な検証→真正B143の実ボクセル/3D出力を1操作で生成。失敗時はモデル出力原本、コンパイラエラー、検査根拠を保存。
- まず既存B198G方式で試し、大規模JSONが小型モデルの障害なら、建築意思決定だけのコンパクトIRを追加。**構造を増やす前に実測**し、既存B143形式を二重管理しない。
- 建築の用途・部屋関係・入口・上下経路はLLM設計由来、形状の厳密座標や建材ブロックは共通エンジン由来として出所を分離。
- 新たな実モデル要求は包括許可済み。ローカル実行経路が利用できない環境なら、接続手順と正確なブロッカーを残し、実推論したふりをしない。

### P2：設計とワールドの橋
- B143 compilerのBuildPlanが常に空なのは**既存の安全契約**。過去の契約を削らず、別モジュールで sourceSha + targetEdition + worldId + anchor + bounds + backupRef + operations + checksum を持つ施工候補を生成する。
- 初回は小さい専用試験区画と少数ブロックで、元世界との差分/復元を確認。次に1棟をチャンク化し、コマンド予算、進捗/停止/リトライ、置換対象保護を確認する。
- 準備性のゲート（対象同定・座標/範囲・原本バックアップ・材質/版対応・安全命令・実行停止・空間品質）が全て確定した場合だけ施工。ユーザー包括許可があっても **NOT_PREPAREDを形だけPASSにしない**。
- Minecraft内の入口/移動/階段/室内を確かめる。実ワールドの自動操作手段がなければ、既存の許可済み試験ワールドに対応する操作と、未実施項目を明記。

### P3：小型Macを後回しにしない
- 8GB Apple Silicon + 2B級4bitを**設計上の最小目標**に据え、16GB + 4B級、OMEN上の大型Qwen/Gemmaを比較群にする。
- 小型モデルの設計IRは短く、用途・階層・関係・外観意図を中心にする。ボクセル座標をすべてモデルに書かせない。
- Mac実機が接続できない場合は、同じ量子化・出力トークン・コンパイル品質の事前測定を行い、実Mac速度/メモリについては**未検証**とする。後日実機でmemory pressure/peak RAM/生成時間を測る。
- 先に2Bが基本建築で実際に成功するか判定し、必要に応じて小型向けの意味IRや決定的な接続補助を改善。小型モデル失敗を大型モデルの成績で隠さない。

## 成果物として残すもの
1. 動くワンステップ入口（コマンドもしくはローカルUI。毎回のZIPと手認証は不要）。
2. 実モデル名称、量子化、要求、設計IR（使う場合）、元モデル応答、B143ソース、3Dメッシュ/レビュー、座標と材料、品質検査、SHA、実行時間、メモリ（測れた範囲）を持つ証拠。
3. 対象ワールドが明確な安全な施工計画。現実の施工を行った場合はバックアップ、差分、実行ログ、ゲーム内画像・機能検証、復元情報。
4. 3用途の比較表。**ソースPASS / 実3D QA / 人間美術 / 世界内歩行 / 実LLMの創造力**を別欄にする。
5. 既存PR #128に小さく意味のあるコード・テストをコミットし、AI_RESTART_JA.mdには現在地・最重要ブロッカー・次の1手だけを更新。

## 未達時の判断規則
- 既存B143ソースのサイズ・形式が障害 → 先に小さい意味IRへ分離し、その出力を既存B143へ変換。LLMの創造部分は維持する。
- 部屋はあるが入口がない → 「入口が存在するか」だけでなく内部から用途空間へ実際に到達できるかを共通検査する。
- 階段が不成立 → 経路の始点・終点・着地点を設計段階に戻す。壁の一枚を無限に修正しない。
- 施工が接続できない → 接続/制約のブロッカーを明記し、まず再生可能なBuildPlanだけ作る。仮の施工完了は宣言しない。
- 2連続の同建物固有修正が必要 → その建物をHOLDして他用途の再現性・汎用的原因へ切替。
- CIが遅い → docsのみの変更で全workflowを再起動しない改善を別途計画。開発の主題をCI最適化にすり替えない。

## 初回MVPの終了条件
- 初見の自然言語指示が**実ローカルLLM**を経由して真正3Dへ変換され、基本用途・入口・床・屋根・窓が現物で見える。
- 試験施工をした場合、技術安全ゲート、元世界の保護、空間/歩行の検証がある。
- 3用途を比較し、良否を明確に記録。**未成功なら「未成功」と書く。**
- 単一の図書館を修正した件数、テスト本数、工程番号だけで完了にしない。
